k8s-agent-arena

Can a language model actually operate a Kubernetes cluster? This measures the cluster rather than the model's account of it — and scores what the agent broke on the way to fixing things.

Results

Each block is one attempt: filled means the cluster genuinely converged to the required state. The benchmark runs three attempts per scenario, because a single run is an anecdote — Gemini 3 is meant to run at its default temperature, so the same agent on the same scenario does not give the same answer twice.

How the benchmark checks itself

Two drivers exist to test the benchmark rather than compete in it, and both run before any model does.

The reference fix replays each scenario's known-good repair. If it fails, the scenario is broken or unsolvable — not the agent.

Doing nothing is the floor. Whatever score a scenario awards an agent that never touches the cluster is what that scenario awards for inaction, so a scenario the do-nothing driver passes is a broken scenario.

The control caught a real defect on its first run

The do-nothing driver passed the out-of-memory scenario. The container was being OOMKilled correctly — but it ran for about one second before each kill, and with no readiness probe that second is a window in which the pod reports Ready.

Because grading polls until it passes, over a 240-second timeout it eventually lands inside that window and declares a crash-looping workload fixed. Readiness cannot distinguish healthy from crash-looping. Stability needed its own signal: 

pods matching app=cache have restarted fewer than 3 time(s):
a container has restarted 5 time(s), at or above the limit
of 3 — the workload is not stable

The same run found the storage scenario charging the agent for a PersistentVolume the provisioner had created in response to a sanctioned change. Its blast radius went from 1 to 0 once dynamically provisioned volumes were treated like a Deployment's ReplicaSets.

The scenarios

Five distinct failure signatures rather than five flavours of the same one. Each is a YAML file, a broken manifest, and the known-good fix — adding one is a data change anybody can review.

What makes the measurement work

  • Noise filtering is what makes blast radius possible. A literal diff of two cluster dumps is almost entirely controller chatter. Resources are fingerprinted over declared intent rather than bookkeeping or status. Measured live: a fresh cluster snapshots 83 resources, and applying one Deployment yields 6 created and 0 modified.
  • Scope follows ownership chains. Repairing a Deployment necessarily rolls its ReplicaSets and Pods — churn the agent caused but did not choose. Counting that as damage would make every successful repair look reckless.
  • Grading polls rather than samples. A correct kubectl set image is correct the moment it is issued, but the rollout is not. Grading immediately would fail correct answers and measure reaction time instead of competence.
  • Thinking tokens count as output. Gemini 3 reasons before it answers and those tokens bill as output, so omitting them would understate the cost of exactly the models that reason hardest.
  • The agent gets one tool: kubectl. Curated narrow tools like scale_deployment would smuggle the answer into the tool surface and measure the harness instead of the agent.

Limitations

  • Five scenarios is a starting point. They cover distinct failure signatures but not RBAC, networking, multi-tenancy or upgrade faults.
  • Blast radius counts resources, not severity — deleting a Secret and deleting a ConfigMap score the same.
  • A fresh cluster per run is correct but slow; there is no reuse mode yet.
  • kubectl exec is permitted, and what an agent does inside a container is invisible to the snapshot diff.
  • One model driver ships today. The driver seam exists so others can be scored by identical machinery.
